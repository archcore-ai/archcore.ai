# Ponytail and Archcore integration benchmark

Reviewed on September 24, 2026. This note supports the
[Ponytail integration](/integrations/ponytail/).

## What was measured

Ponytail pushes an agent toward the shortest working change and flags code that
can be deleted. Archcore keeps the project's accepted decisions. The benchmark
asked whether a short instruction text keeps both behaviors when they meet:
Ponytail wants to cut code that an accepted decision requires, or the user
settles a decision that nothing records.

Every arm had both tools installed. The reference arm had no cooperation
instructions. Each other arm appended one instruction draft to `AGENTS.md`. All
arms in one task ran inside one frozen experiment, in shuffled order, five runs
each.

Host: Claude Code 2.1.281. Model: `claude-sonnet-5` at medium effort, with a
spend cap of $0.50 per run. Archcore CLI and plugin: 0.10.3. Ponytail plugin:
4.10.0 in `full` mode. The project was a small synthetic Python quotation
library with one accepted decision: money is integer cents.

## The four tasks

| Task                     | Request                                                                                    | Correct result                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| Review with a buried ADR | Review a branch for over-engineering. Use `ponytail-review` if available. Change no files. | Keep `DeliveryPolicy`, which an accepted ADR requires for partner packages. Cut the unjustified `PriceSource` factory next to it. |
| Settled removal          | "The owner decided to drop gift wrapping" and remove it from `quote()`.                    | Remove the feature, keep the tests passing, and record the decision in one new draft ADR.                                         |
| Same removal, reworded   | "Gift wrapping is going away" and take it out. No "owner", "decided" or "drop".            | Same as the settled removal.                                                                                                      |
| Rename                   | Rename the `assemble` helper to `build_quote`.                                             | Rename it and create no record: there is no decision to record.                                                                   |

In the review task the ADR was 120 days old, named no file path and sat among
ten unrelated accepted records, so the session recap did not list it. The agent
could find it only by searching.

## Results for the published instructions

The published instructions have SHA-256
`e649d9aa73f4c2376ffbe827571f0dfd06747b514dab8268a3de28620a84ddcb`.

| Task                     | Published instructions | Both tools, no instructions |
| ------------------------ | ---------------------- | --------------------------- |
| Review with a buried ADR | 5 of 5                 | 0 of 5                      |
| Settled removal          | 5 of 5                 | 0 of 5                      |
| Same removal, reworded   | 5 of 5                 | 0 of 5                      |
| Rename, no record        | 5 of 5                 | 4 of 5                      |

In each of the first three tasks the difference is significant at 5 runs per
arm (two-sided Fisher exact test, Holm-adjusted across the arms of that
experiment, p < 0.05). In every
settled-removal run the new record was one draft ADR, for example
`.archcore/shop/drop-gift-wrapping.adr.md`. The accepted integer-cents ADR was
unchanged in every run. No run wrote a `PONYTAIL-DEBT.md`.

The one failed rename without instructions was an agent error unrelated to
either tool. A `sed` command with `\b`, which BSD `sed` does not support,
changed nothing, and the agent reported the rename as done. The same command
failed the same way once with an instruction draft that has no recording rule.

## How the instructions were chosen

Six drafts ran against the reference arm.

In the review task, all six drafts kept `DeliveryPolicy` in 5 of 5 runs, against
0 of 5 without instructions. The review could not rank them.

In the settled-removal task, five drafts recorded nothing in any of their 25
runs, and neither did the reference arm. None of those drafts told the agent to
record a decision stated in the request. The sixth draft, now published, adds
one rule for this and recorded the decision in 5 of 5 runs. It is the shortest
draft plus that rule.

The recording rule was written after the settled-removal task exposed the gap.
The reworded removal and the rename were run afterwards as held-out checks: one
for a request that avoids the rule's wording, one for a change with nothing to
record.

## How the runs were graded

The review answers were graded by `claude-haiku-4-5-20251001`, which saw only
the answer text. Before use, its keep-or-cut verdicts matched proposed labels on
48 earlier answers. Another model wrote those labels, and a person has not yet
confirmed them. Regular-expression markers ran beside the judge as a
cross-check. In the review experiment they disagreed on 5 of 35 answers. Each
of those answers was read, and in each the markers were wrong. The other three tasks were graded from the final files and
the test suite, with no model involved.

## What these results do not establish

- Five runs per arm detect large differences only. A draft that fails one run
  in five cannot be told apart from one that never fails.
- One model at one effort level in one host. Other models, hosts and versions
  were not tested.
- All four tasks were single requests on one small project. Multi-step feature
  work, long sessions and larger repositories were not tested.
- The settled decisions were all removals stated plainly with a reason.
  Decisions to adopt, replace or defer something, or decisions settled in the
  middle of a conversation, were not tested.
- A later session reading the recorded ADR was not run.
- The review task found the ADR by searching for symbol names that the ADR
  contains. A decision that names none of the affected symbols was not tested.
